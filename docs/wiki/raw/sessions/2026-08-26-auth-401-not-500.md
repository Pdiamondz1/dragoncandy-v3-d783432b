# An auth failure is not a server error: 401 instead of 500 across 20 edge functions

**Date:** 2026-08-26
**Type:** session extract (code change + deploy; PR #542, merged `ced582f4`, all 20 deployed)

## What was wrong

These functions share one shape: a big `try` whose `catch` returns
`error.message` with a **single hardcoded status**. Every failure therefore
became a 500 — a missing `Authorization` header, a bad campaign id, and a
genuinely broken Stripe key all reported identically as "the server broke".

Measured on prod before the change: **twelve** functions answered an
unauthenticated request `500 {"error":"No authorization header provided"}`, and
`get-stripe-dashboard-link` answered 400. The body already named the problem;
only the status disagreed.

**Why it matters beyond tidiness:** a 500 is the one status a client may retry
and monitoring may page on. An auth failure is neither retryable nor an
incident, so the wrong status makes a routine event indistinguishable from an
outage — on the payout and escrow surface, where a real outage is exactly what
someone needs to be able to see.

## The scope went five → fourteen → eighteen → twenty, and each step has a cause

1. **"Five" was my own earlier figure**, taken from a probe of only the twelve
   money functions carrying the `.io` CORS defect. A count bounded by a
   *previous investigation's sample* rather than by this defect.
2. **Grepping the error message found fourteen.**
3. **The fleet guard found four more** that a message-based grep structurally
   could not: the same `if (!authHeader) throw new Error(` shape with a
   different message (`"No authorization header"`, no *provided*). This is the
   argument for a guard that walks the function tree instead of checking a list.
4. **Codex found the branch I had missed entirely** — see below — which added
   two more.

## Codex found the more common failure

Typing the `!authHeader` throw only fixes a **missing** credential. A header
that is present but **invalid or expired** takes a different branch —
`if (userError || !userData.user) throw ...` — which stayed bare, so a rejected
token still reported 500. Tokens expire; that is the commoner of the two.

**The lesson is about the guard, not the bug.** It matched ONE syntactic shape,
so it could only ever vouch for that shape. **A guard's silence means "nothing
matched my pattern", never "nothing is wrong."**

## The design, and what it deliberately does not do

`HttpError` + `unauthorized()` + `statusFor(error, fallback)` map
**authentication** failures to 401 and change nothing else. Authorization
("You are not authorized to verify this campaign"), not-found and validation
failures all keep the function's existing generic status, which the `fallback`
parameter preserves per function — which is why `get-stripe-dashboard-link`
passes 400 rather than being silently promoted to 500.

**Three functions already returned 401 — by string-matching the error message**
(`msg.includes("authorization")`). Correct today, and silently a 500 the moment
anyone rewords the message. The typed error is now authoritative and the
heuristic is KEPT as the fallback for the other throws it also covers, so
behaviour is unchanged and the auth case stops depending on prose.

**No client behaviour changed.** Every caller uses
`supabase.functions.invoke()` and destructures `{ data, error }`; supabase-js
turns any non-2xx into the same `FunctionsHttpError`. Checked before changing
anything: nothing in `src/` branches on a status code, and there is no global
401 interceptor or auto-signout to trip.

## What the guard claims, and what it does not

Two patterns, covering the missing-credential and rejected-credential shapes.
The one exclusion is **named**: `suggest-package`, not a money endpoint and
already 401 behind `verify_jwt = true`.

A **third** shape is deliberately not claimed: `donny-campaign-preview` and
`donny-schedule` throw a bare `new Error("Unauthorized")` with no `userError` on
the line. Each has multiple catch blocks per handler, so wiring them is a
materially larger change on a different surface, and both already answer 401.
**The comment says so rather than implying full coverage** — the exclusion list
is exactly what the two patterns match, not everything that is unfixed.

The `PARKED` list was first written from memory and named those two files. The
**exact-equality** assertion rejected it, because they never matched the
patterns at all. A subset check would have accepted the wrong list silently.

## A line-ending trap

These files are a **per-file mix of CRLF and LF**, a legacy of the repo's move
from Windows. A naive Python read/write rewrote them all to LF — **1,777
phantom line changes** across the payout and escrow surface on the first
attempt, which was reverted. A diff that size is unreviewable, which is the same
outcome as not being reviewed. The script round-trips each file's own ending;
the real diff is ~80 lines.

## Deploy verification

`verify_jwt` was checked **before** deploying, because the dangerous combination
is a function that is live `false` but **absent** from `config.toml` — the
deploy would then apply the platform default `true` and the function would start
rejecting its own callers. Checked all 20: **fifteen** declared `false` and live
`false`; one declared `true` and live `true`; four absent and live `true`, which
the default matches. 15 + 1 + 4 = 20. **No function was live-false-but-absent**,
so the deploy preserved every posture. Confirmed unchanged afterwards.

(That breakdown first read "fourteen", which sums to 19 against a stated 20 —
`donny-chat` is declared `false` and I dropped it counting by eye. Caught by the
Codex second review. **Third arithmetic slip of the day on a stated total**, and
the same shape each time: the buckets were right and the sum was never checked.
The fix is mechanical — `awk | sort | uniq -c` over the probe output — not more
care.)

Every upload log carried `http-error.ts` in its asset list — the evidence the
fix shipped rather than the deploy reusing an old bundle.

| group | before | after |
|---|---|---|
| 12 money functions | 500 | **401** |
| `get-stripe-dashboard-link` | 400 | **401** |
| 5 behind `verify_jwt = true` | 401 | 401 (unchanged) |
| `donny-chat` (heuristic) | 401 | 401 (unchanged) |
| `refund-package-order`, `release-package-payout` | 500 | 500 — see below |

CORS still answers `capacitor://localhost` on all 20, so the earlier fixes held.

## The two that did NOT move, and why that is a finding rather than a failure

`refund-package-order` and `release-package-payout` still answer
`500 {"error":"Missing required field: orderId"}`. That is **not** the fix
failing — their auth check is never reached.

Proven rather than assumed, by supplying the field:

```
empty body : {"error":"Missing required field: orderId"}                            [500]
with field : {"error":"Order not found: Cannot coerce the result to a single JSON"}  [500]
```

So the order is: parse body → **look up the order with a service-role client** →
*then* authenticate. **An unauthenticated caller can therefore distinguish
"order exists" from "order not found".** That is an existence oracle on a
service-role read, and it is worse than the "validates the body before auth"
note this was previously filed under.

**The naive fix would break guest refunds.** The branch above the auth check
compares `order.buyer_guest_token`, so the order genuinely must be fetched
before the caller can be identified — a guest buyer has no JWT. The correct fix
is to stop *leaking* existence (return one indistinguishable error for both
"not found" and "not a participant"), not to move the auth check up. Bounded in
practice because `package_orders.id` is a UUID and not enumerable.

Left for its own change, with the mechanism recorded so the next session does
not reach for the reordering that breaks guests.

## The durable lesson

**A count inherited from an earlier investigation carries that investigation's
sample, not the current question's.** "Five" was never wrong as a statement
about the twelve money functions probed for a CORS defect; it was wrong as a
statement about this defect, and nothing in the number itself said which it was.
Re-derive scope from the defect, not from the last time someone counted.
