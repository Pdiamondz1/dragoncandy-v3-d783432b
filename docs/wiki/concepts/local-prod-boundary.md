# Local/Production Boundary & Repo Joinability

**For the whole life of this project, `npm run dev` connected to the production database.** Nobody
noticed, because for the whole life of this project there was one developer, and he wanted prod
data anyway.

It surfaced on 2026-08-19 — not from a bug, but from writing the hiring plan
(`docs/DragonCandy_Tech_Department_Scope.md`). Auditing whether the repo was ready for staff
answered *no*, and this was the reason. **A hazard whose only mitigation is "there is only one of
us" becomes a defect the moment you hire.**

## The two causes, both pointing at prod

1. **`.env` is tracked.** It appears in `.gitignore` (line 19) but was committed before that rule
   existed, and **`.gitignore` does not untrack an already-tracked file.** It ships in every clone
   carrying `VITE_SUPABASE_URL="https://zocahiffooqdybdhguqv.supabase.co"`.
2. **`client.ts` fell back to prod** when the variable was unset.

So both the configured path and the unconfigured path led to live customer data, with no warning
and no opt-in. **Checking `.gitignore` is not checking whether a file ships** —
`git ls-files --error-unmatch .env` is.

## The fix, and why it is safe

A dev-only guard in `src/integrations/supabase/client.ts` that throws at import time. Three
conditions matter:

- `import.meta.env.DEV` — so Vite statically evaluates it to `false` in a production build and
  **dead-code-eliminates the whole block**. Verified by grepping `dist/` for the guard's message
  and for the staging host: both absent. Production behaviour is not "believed unchanged", it is
  *provably absent*.
- `MODE !== 'test'` — without it, a module-scope throw breaks every one of the 243 test files that
  transitively import the client.
- `VITE_ALLOW_PROD_FROM_LOCAL !== 'true'` — a deliberate, per-session escape hatch. A guard with no
  escape hatch gets deleted by the first person it inconveniences.

## The lesson worth keeping: a safety control that fails open is worse than none

The first implementation compared strings:

```ts
SUPABASE_URL === PROD_SUPABASE_URL   // WRONG
```

The mandatory Codex second review (`CLAUDE.md`, the `codex-review` skill) flagged it P1. `https://zocahiffooqdybdhguqv.supabase.co/` — same project,
one trailing slash — is not string-equal, so the guard waved it through. So did different casing,
an explicit `:443`, an added path, a query string, and a fragment.

**This is worse than having no guard**, because it also manufactures the belief that the hazard is
handled. Nobody re-checks a problem they think is solved.

The rule now compares **hostnames**, in a separately tested module
(`src/lib/supabaseEnvGuard.ts`, 19 tests):

```ts
new URL(url).hostname.toLowerCase() === PROD_SUPABASE_HOST
```

Two design choices in that module are load-bearing:

- **Unparseable input fails closed.** `classifySupabaseUrl` returns `'unparseable'` rather than
  `'other'`, so a caller cannot mistake "we could not tell" for "it is safe."
- **Host equality, not substring.** `zocahiffooqdybdhguqvx.supabase.co` and
  `zocahiffooqdybdhguqv.supabase.co.evil.test` both *contain* the prod ref and are both different
  projects. A substring check would fail closed on legitimate targets — the mirror-image bug.

It was extracted out of `client.ts` rather than left inline because `client.ts` creates the client
as an import side effect (so it resists unit testing) and still carries a Lovable-era
`// This file is automatically generated. Do not edit it directly.` header. **If Lovable ever
regenerates that file the guard vanishes silently** — noted in `docs/runbooks/qa-staging-gate.md`,
and the reason the rule itself lives somewhere a regeneration cannot reach.

## The wider finding: "joinable" is a property you have to check for

The same audit found the repo had no `CONTRIBUTING.md`, no architecture map and no first-week
guide; a `README.md` describing a product that does not exist (a "ChatGPT-4o Copilot", AI video
scene detection, LinkedIn publishing); a dead `product-roadmap.md` at 0 of 72 tasks describing a
design system never built; and no Node pin, so a new hire on Node 26 would open the repo to **50
failing tests** that CI's Node 24 passes.

None of these are bugs. Every one of them is invisible to the person who already knows the answers.
**Solo-developer repositories accumulate this debt silently, and the only reliable detector is
someone arriving** — which is exactly when it costs the most. Closed with `CONTRIBUTING.md`,
`docs/ARCHITECTURE.md`, `docs/onboarding/first-week.md`, PR/issue templates, `.nvmrc` + `engines`,
and a truthful README.

Related, and found the same way: the repo **disagrees with itself** on a Supabase key name. `.env`
and `.env.example` define `VITE_SUPABASE_PUBLISHABLE_KEY`; every call site reads
`VITE_SUPABASE_ANON_KEY`. `client.ts` survived on its hard-coded fallback, so nothing failed
loudly — but five hooks pass the variable straight into an `apikey` header with no fallback, which
is `undefined` locally. `client.ts` now accepts either name; the five hooks still read the env var
directly.

## Known issues

- **`.env` is still tracked**, which is the root cause. Untracking it requires first confirming
  Vercel's Production scope supplies all five `VITE_` variables rather than quietly relying on the
  committed file for `VITE_GOOGLE_MAPS_API_KEY` / `VITE_RECAPTCHA_SITE_KEY`. That could not be
  verified without dashboard access, so it was **deferred rather than guessed** — the guard closes
  the hazard without needing the answer.
- **The committed staging password is not rotated.** It sits in three tracked files and is already
  flagged compromised in [[QA CI/CD Gate]]'s runbook.
- **Five hooks still read `VITE_SUPABASE_ANON_KEY` directly** instead of the exported constant.
