# Auto Cross-Scheduling: Spread Campaign Deliverables Across Posting Days

**Date:** 2026-05-26
**Status:** Draft
**Author:** Dame Williams + Claude

## Context

Campaigns on DragonCandy often produce multiple deliverables (e.g., 3 pieces of content: a reel, a photo, a carousel). After content is approved and the creator is paid, the restaurant needs to spread those deliverables across different days for maximum social media impact rather than posting them all at once. Today, the system fires a single "content approved" social hook and the restaurant has to manually manage when each piece goes live. This feature adds scheduled content spreading — pre-configured at campaign creation, auto-generated by Donny after content approval, and adjustable by the restaurant at any time.

## Requirements

### Core
- Restaurant pre-configures posting spread preferences at campaign creation (strategy + preferred days)
- After content approval, Donny auto-generates a posting schedule based on those preferences and platform best practices
- Restaurant reviews and adjusts the schedule (dates, times, captions) before confirming
- Each deliverable posts to ALL connected platforms on its scheduled day (Donny auto-adapts captions per platform)
- Creator and brand receive date-specific notifications so they can optionally align their own posts
- Full rescheduling flexibility for unpublished posts after confirmation

### Non-Goals
- Multi-party synchronized scheduling (creator/brand not required to post on restaurant's schedule)
- Per-platform assignment per deliverable (all platforms on each scheduled day)
- Engagement analytics on scheduled posts (future scope)

## Architecture: Campaign Preferences + Existing Posts System

Reuses the existing `donny_scheduled_posts` table and `content-posting-plan` edge function. No new tables.

### Data Model Changes

**1. Add `posting_preferences` JSONB to `campaigns` table:**

```json
{
  "spread_strategy": "custom",
  "spread_window_days": 14,
  "preferred_days": ["tuesday", "saturday", "monday"],
  "auto_schedule_on_approval": true
}
```

Fields:
- `spread_strategy`: `"auto"` (Donny decides everything — maps to "Let Donny decide" UI default), `"even"` (space evenly), `"front_loaded"` (cluster early), `"custom"` (user picks days)
- `spread_window_days`: `7 | 14 | 21 | 30`
- `preferred_days`: array of lowercase day names, used when strategy is `"custom"` or as hints for AI
- `auto_schedule_on_approval`: if `true`, Donny auto-generates the schedule on content approval (restaurant still reviews before posts go live)

**2. Add `deliverable_id` UUID to `donny_scheduled_posts`:**

- Nullable FK referencing `campaign_deliverables(id)`
- Links each scheduled post to the specific deliverable it publishes
- Backward compatible — existing posts without deliverables unaffected

**3. Add `posting_schedule_status` TEXT to `campaigns`:**

- Values: `not_configured | configured | pending_review | scheduled | in_progress | completed`
- `not_configured`: no preferences set (default)
- `configured`: preferences set at creation, waiting for content approval
- `pending_review`: draft schedule generated after content approval, awaiting restaurant confirmation
- `scheduled`: restaurant confirmed the posting schedule, posts queued with Outstand
- `in_progress`: at least one post published, others pending
- `completed`: all scheduled posts published

**4. Add `deliverable_id` UUID to `campaign_social_hooks`:**

- Nullable FK referencing `campaign_deliverables(id)`
- Required to support multiple date-specific stage 4 hooks per user per campaign
- Existing unique constraint `UNIQUE(campaign_id, stage, user_id)` must be replaced with `UNIQUE(campaign_id, stage, user_id, deliverable_id)` to allow one hook per deliverable per user

### Migration

```sql
-- Add posting_preferences and posting_schedule_status to campaigns
ALTER TABLE campaigns
  ADD COLUMN IF NOT EXISTS posting_preferences JSONB,
  ADD COLUMN IF NOT EXISTS posting_schedule_status TEXT DEFAULT 'not_configured'
    CHECK (posting_schedule_status IN (
      'not_configured', 'configured', 'pending_review',
      'scheduled', 'in_progress', 'completed'
    ));

-- Add deliverable_id to donny_scheduled_posts
ALTER TABLE donny_scheduled_posts
  ADD COLUMN IF NOT EXISTS deliverable_id UUID REFERENCES campaign_deliverables(id);

-- Add deliverable_id to campaign_social_hooks and update unique constraint
ALTER TABLE campaign_social_hooks
  ADD COLUMN IF NOT EXISTS deliverable_id UUID REFERENCES campaign_deliverables(id);

ALTER TABLE campaign_social_hooks
  DROP CONSTRAINT IF EXISTS campaign_social_hooks_campaign_id_stage_user_id_key;

ALTER TABLE campaign_social_hooks
  ADD CONSTRAINT campaign_social_hooks_campaign_stage_user_deliverable_key
    UNIQUE (campaign_id, stage, user_id, deliverable_id);
```

All columns are nullable, no data backfill needed, no risk to existing data. The unique constraint change is backward compatible — existing rows have `deliverable_id = NULL` which remains unique under the new constraint.

### TypeScript Type Changes

The following types need updating after the migration:
- Supabase generated types (`src/integrations/supabase/types.ts`) — regenerate after migration
- `EditableCampaign` interface (`src/types/campaignCreator.ts`) — add `posting_preferences` field

### Multi-Creator Campaigns

Campaigns can have multiple accepted creators, each with their own `campaign_collaboration`. The posting schedule is **per-collaboration**: when a specific creator's content is approved, a schedule is generated for that collaboration's deliverables only. If a second creator's content is approved later, a separate schedule is generated for their deliverables. Each schedule gets its own `plan_group_id`. The `posting_schedule_status` on the campaign reflects the aggregate state — it moves to `completed` only when all collaborations' schedules are complete.

### 3. Campaign Detail Page: Schedule Section

New section on the campaign detail page, visible when `posting_schedule_status !== 'not_configured'`:

- **`pending_review` state**: "Your posting schedule is ready to review" CTA card. Links to the schedule review screen.
- **`scheduled` / `in_progress` state**: Compact timeline with status summary: "1 of 3 posted — next post Saturday 6:00 PM". Tap to open full schedule review for editing.

## Backend Flow

### Interaction with Existing Stage 4 Hooks

The existing `ContentReviewSection.tsx` calls `fire-campaign-social-hook` with `stage: 4` immediately after content approval. This creates single-shot `donny_scheduled_posts` drafts and social hooks for all parties. When `campaigns.posting_preferences` exists and `auto_schedule_on_approval = true`, the existing stage 4 auto-draft behavior for the **restaurant** must be skipped — the new spread-schedule flow replaces it. Creator and brand stage 4 hooks (non-date-specific) still fire as usual for their independent cross-posting.

Implementation: `fire-campaign-social-hook` checks `campaigns.posting_preferences` at the start of stage 4 processing. If preferences exist, it skips the restaurant's auto-draft creation and instead calls the schedule generation flow below. Creator/brand hooks proceed unchanged.

### Schedule Generation (after content approval)

**Orchestrator:** The `release-creator-payout` edge function is extended. After successfully releasing payment, it checks `campaigns.posting_preferences`. If present and `auto_schedule_on_approval = true`, it calls `content-posting-plan` via internal HTTP fetch with service-role auth (matching the existing pattern where `fire-campaign-social-hook` calls `social-caption` via `fetch(${SUPABASE_URL}/functions/v1/social-caption, ...)`). The `content-posting-plan` function must skip rate limiting for service-role callers (check `Authorization: Bearer <service_role_key>` vs user JWT). This keeps schedule generation fully server-side — no client involvement needed for the auto-trigger.

Flow:
1. Restaurant approves content → `release-creator-payout` executes → `content_status = 'approved'`
2. `release-creator-payout` checks `campaigns.posting_preferences`:
   - If absent or `auto_schedule_on_approval = false`: skip (existing behavior, restaurant can manually trigger from campaign detail page later)
   - If present and `auto_schedule_on_approval = true`: continue to step 3
3. Call `content-posting-plan` internally with:
   - Approved deliverables for this collaboration (URLs, content types, mime types)
   - `posting_preferences` from campaign (strategy, window, preferred days)
   - Connected platforms from `business_outstand_accounts`
   - Restaurant timezone (from state → IANA mapping, already built)
4. `content-posting-plan` generates `PlannedPost[]` with AI-optimized times respecting preferences and returns them
5. `release-creator-payout` persists results: insert `donny_scheduled_posts` entries with `status = 'draft'`, `deliverable_id` set, `plan_group_id` linking them, `campaign_id` set
6. Set `campaigns.posting_schedule_status = 'pending_review'`

If `posting_preferences` are absent, the restaurant can still trigger schedule generation manually from the campaign detail page. This calls `content-posting-plan` from the frontend with default preferences (even spread, 2 weeks) and persists drafts via the existing `useDraftPosts` mutation.

### Schedule Confirmation

1. Restaurant reviews schedule in the Timeline + Cards UI and taps "Confirm & Schedule All Posts"
2. Frontend calls a new `confirm-posting-schedule` edge function (or extends `outstand-proxy`) with the `plan_group_id`
3. For each draft post in the plan group:
   - Call Outstand API via `outstand-proxy` to queue the post at the scheduled time
   - Store the returned Outstand post ID in `donny_scheduled_posts.metadata.outstand_post_id`
   - Update `donny_scheduled_posts.status = 'scheduled'`
4. Set `campaigns.posting_schedule_status = 'scheduled'`
5. Fire date-specific `campaign_social_hooks` for creator and brand — one hook per posting date per party, with `deliverable_id` set (uses new unique constraint)
6. Create/update `triple_post_sessions` entries

### Post Publishing

1. Outstand publishes posts at scheduled times
2. Webhook/polling updates `donny_scheduled_posts.status = 'published'`, sets `published_at`
3. Log to `social_post_log` for audit trail
4. When first post publishes: `campaigns.posting_schedule_status = 'in_progress'`
5. When all posts published: `campaigns.posting_schedule_status = 'completed'`

### Creator/Brand Notifications

- On schedule confirmation: create `campaign_social_hooks` records for each posting date (stage 4 variant, with `deliverable_id` set)
- Hook content template: "La Cocina is posting your [content_type] tomorrow at [time]. Boost engagement by sharing your version!"
- Sent 24 hours before each posting date
- Creator/brand actions: "Post Now" | "Skip" (existing hook status flow)
- Updates `triple_post_sessions` when creator/brand posts their version

### Rescheduling

- Restaurant edits a post → update `donny_scheduled_posts` (date, time, caption)
- If date changes and post was already scheduled with Outstand:
  - Cancel old Outstand schedule via `DELETE /v1/posts/{outstand_post_id}` through `outstand-proxy`
  - Re-queue at new time, store new `outstand_post_id` in metadata
- If creator/brand had a notification for the old date: update or cancel the corresponding `campaign_social_hooks` record (matched by `deliverable_id`), create new one for the new date
- Canceling a post: set `donny_scheduled_posts.status = 'cancelled'`, cancel Outstand schedule if queued

## Edge Function Changes

### `content-posting-plan` (extend)

Add `posting_preferences` to `PlanRequest` interface:
```typescript
interface PlanRequest {
  // ... existing fields ...
  posting_preferences?: {
    spread_strategy: 'auto' | 'even' | 'front_loaded' | 'custom';
    spread_window_days: number;
    preferred_days?: string[];
  };
  deliverables: Array<{
    // ... existing DeliverableInput fields ...
    deliverable_id: string; // campaign_deliverables.id — passed through to output
  }>;
}
```

Add `deliverable_id` to `PlannedPost` return type:
```typescript
interface PlannedPost {
  // ... existing fields ...
  deliverable_id: string; // mapped from input deliverable
}
```

Strategy handling:
- When `spread_strategy = 'auto'`: Donny decides strategy, window, and days based on content type mix and platform best practices
- When `spread_strategy = 'custom'` and `preferred_days` provided: assign deliverables to those days within the spread window
- When `spread_strategy = 'even'`: distribute deliverables evenly across the window
- When `spread_strategy = 'front_loaded'`: cluster posts in the first third of the window
- Always apply platform-specific optimal time rules (already built)
- Each input deliverable's `deliverable_id` is passed through to its corresponding `PlannedPost` output for linking
- Function remains stateless (returns data, does not persist) — caller is responsible for inserting `donny_scheduled_posts`
- Skip rate limiting when called with service-role auth (internal calls from `release-creator-payout`)

### `fire-campaign-social-hook` (extend)

Conditional bypass for restaurant auto-drafts:
- At the start of stage 4 processing, query `campaigns.posting_preferences` for the campaign
- If preferences exist with `auto_schedule_on_approval = true`: skip restaurant auto-draft creation (the spread-schedule flow in `release-creator-payout` handles it)
- Creator and brand hooks proceed unchanged

Add support for date-specific hooks:
- Accept optional `scheduled_dates` array: `[{ deliverable_id, posting_date, content_type }]`
- Create one hook per posting date per party using new `deliverable_id` column (instead of a single stage 4 hook)
- Uses updated unique constraint `UNIQUE(campaign_id, stage, user_id, deliverable_id)`
- The existing upsert `onConflict: 'campaign_id,stage,user_id'` must be updated to `onConflict: 'campaign_id,stage,user_id,deliverable_id'` — this applies to both the new date-specific path and the existing non-spread path (which passes `deliverable_id = null`)
- Hook content template references the specific deliverable and date

### `release-creator-payout` (extend)

After successful payment release:
- Query `campaigns.posting_preferences` for the campaign
- If present and `auto_schedule_on_approval = true`:
  - Query approved deliverables for this collaboration from `file_uploads` (where `file_category = 'deliverable'` and `campaign_id` matches)
  - Call `content-posting-plan` as an internal function with deliverables + preferences
  - Insert returned `PlannedPost[]` as `donny_scheduled_posts` rows with `status = 'draft'`, `deliverable_id`, `plan_group_id`, `plan_order`
  - Update `campaigns.posting_schedule_status = 'pending_review'`
