Implementation Approach

Three ways to execute the full UX theme update across ~50 pages + components. Each uses team sub-agents as requested.

A

🏗️ Foundation-First (Recommended)

Phase 1: Build the theme foundation — update Tailwind config, global CSS, fonts, logo asset, shared components (Button, Card, Nav, Layout). This changes everything at once through the design system.

Phase 2: Screenshot-matched pages — pixel-match the 8 pages with screenshots (Landing, Login, Dashboard, Browse Creators, Portfolio, Profile, Messaging, Campaigns swipe view).

Phase 3: Remaining pages — apply the theme to all other pages (~40) using established patterns. Parallel sub-agents grouped by domain (settings pages, project pages, etc.).

Pros: Foundation changes cascade everywhere. Less rework. Sub-agents in Phase 3 work from a stable base.
Cons: Phase 1 is sequential (can't parallelize the foundation). Slightly longer before first visible page.

B

⚡ Page-Parallel Blitz

Update Tailwind config + fonts + logo first (quick foundation), then immediately dispatch parallel sub-agents — each agent owns a page group and applies the theme independently.

Sub-agents: Landing+Login agent, Dashboard agent, Browse+Portfolio agent, Messaging agent, Campaigns agent, Settings group agent, Projects group agent, etc.

Pros: Maximum parallelism. Fastest wall-clock time.
Cons: Risk of inconsistency between agents. Shared components may get conflicting changes. Merge conflicts likely. Needs careful coordination.

C

🎯 Component-Out Strategy

Work exclusively through shared components. Update every shared UI component (Button, Card, Input, Badge, Avatar, Nav, Layout, Sheet, Dialog, etc.) to match the design system. Pages mostly update themselves because they consume these components.

Then do a focused pass on the 8 screenshot pages for page-specific layouts (campaign swipe, messaging bubbles, profile hero, etc.).

Pros: Highest consistency. Component changes propagate to all pages. Minimal per-page work.
Cons: Doesn't handle page-level layout changes (backgrounds, section ordering). Still need per-page work for screenshot pages.

My recommendation: Option A (Foundation-First). It combines the best of B and C — we build the foundation (config + shared components) first so changes cascade, then use parallel sub-agents for the page-specific work. This gives us consistency AND speed where it matters.
