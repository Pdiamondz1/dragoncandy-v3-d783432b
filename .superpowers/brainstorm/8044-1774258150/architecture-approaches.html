How should we architect Donny?

Three approaches — from lightweight to full platform. Each has different trade-offs on speed, cost, and capability.

A

Edge Function Agent (Recommended)

Donny runs as a Supabase Edge Function that wraps GPT-4o with function-calling. Each user message hits an edge function that:

  • Loads user context from Supabase (profile, campaigns, history)
  • Builds a system prompt with Donny's personality + available tools
  • Calls GPT-4o with function definitions (create_campaign, match_creators, etc.)
  • Executes tool calls against Supabase, then returns Donny's response
  • Streams responses back via Supabase Realtime for a live chat feel

Pros

  • Stays in your existing stack — no new infra
  • Function-calling is battle-tested with GPT-4o
  • Conversation history stored in existing messages table
  • Streaming via Supabase Realtime you already use

Cons

  • Edge function cold starts (mitigated by warm-up)
  • Complex multi-step flows need careful prompt engineering
  • 10-minute edge function timeout for long operations
B

OpenAI Assistants API

Donny is an OpenAI Assistant with persistent threads. Each user gets a thread, and OpenAI manages conversation memory and tool execution:

  • Create an Assistant with Donny's personality and tool definitions
  • Each user conversation = an OpenAI Thread (persistent memory)
  • Tools call back to Supabase Edge Functions for data/actions
  • OpenAI handles context window management and tool orchestration

Pros

  • OpenAI manages conversation memory automatically
  • Built-in tool orchestration and retry logic
  • File search and code interpreter available if needed later

Cons

  • Vendor lock-in to OpenAI's Assistants API
  • Less control over streaming and response timing
  • Thread data lives on OpenAI servers (privacy consideration)
  • Additional API cost on top of token usage
C

Hybrid Client + Edge

Split Donny's brain between the client (for fast UI interactions) and edge functions (for data-heavy operations):

  • Client-side: lightweight prompt handles quick replies, UI suggestions, navigation
  • Edge function: heavy operations (campaign creation, creator search, payments)
  • Client decides if a message needs the server or can be handled locally
  • Pre-fetched user context cached on client for instant responses

Pros

  • Fastest perceived response time — some replies are instant
  • Reduced API costs for simple interactions
  • Works partially offline

Cons

  • API key exposure risk on client (needs proxy regardless)
  • Two codepaths to maintain — complexity doubles
  • Context sync between client and server state
  • Over-engineered for v1
